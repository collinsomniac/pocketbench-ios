# Agent skill: Maximum Useful Browser Throughput

**Trigger:** a request to optimize GPU/CPU computing, browser 3D, games, visualization, fluid/particle simulation, image processing, or in-browser inference on a concrete device. **Reference:** [PERFORMANCE_FIELD_GUIDE.md](PERFORMANCE_FIELD_GUIDE.md). Use the field guide's source links for API claims and its labeled phone measurements for device-specific claims. This is a project instruction, not a claim that any untested optimization is already verified.

## Mission

Maximize **correct completed work per wall second**, and account for the value and cost of resulting data. Do **not** assume display refresh is the throughput target. Never impose a 60/120 FPS cap as an optimization strategy unless the product explicitly requires it. Offscreen textures, resident GPU data, worker compute, lower-resolution solver grids, precomputation and batching are first-class outcomes—not invisible compromises. Report visible presentation separately only if it is part of the product's output contract.

## Mandatory seven-stage procedure

1. **Define a completed unit and observation requirement.** Examples: one correct simulation step, one fluid cell update, one distinct GPU-resident output texture, one correctly inferred token, one composited picture. Is it enough to retain latest state, sampled images, all images, a reduced feature, or CPU-readable output? State simulation timestep and correctness tolerance independently of wall-time benchmark throughput. Do not rename GPU submissions 'FPS'.
2. **Probe the actual deployment.** Record exact URL, Safari/Chrome/embedded context and UA with caveats; viewport/canvas CSS dimensions × DPR and real framebuffer; `navigator.gpu`, adapter/device features and limits (they can differ), `timestamp-query`, `shader-f16`, renderable formats, WebGL extensions, `OffscreenCanvas`, `crossOriginIsolated`, `SharedArrayBuffer`, hardwareConcurrency (only browser-exposed), and `device.lost`. Don't assert actual VRAM, GPU clocks/cache or temperature from browser data. WebGPU requestDevice required features/limits must be tested.
3. **Construct equivalent baseline paths.** JS typed arrays, Wasm+SIMD/threads only if usable, WebGL2 fragment/FBO/transform feedback where expressible, WebGPU compute/render. Include data preparation, uploads, GPU execution, resource conversion, readback, and output consumer. A tiny CPU problem may beat GPU setup. Keep independent render and compute controls.
4. **Instrument the bottleneck:** per-pass timestamp medians/P90 when available; CPU encode/submit; end-to-end completed units/s by bounded batches plus queue/fence completion; output/correctness spot checks; in-flight depth and memory/resource allocation; both cold-start and warmed rates. For WebGPU `onSubmittedWorkDone` is a benchmark batch throttle, not a production requirement every frame. Save raw arrays and case config. Repeated, paired ABBA runs beat one number.
5. **Select optimizations based on cost model.** Ask what dominates: O(N²) interactions, global memory bandwidth, fragments/overdraw, draw/dispatch count, driver/JS calls, format conversion, CPU↔GPU copy, sync, transient allocation, or browser presentation. Choose a small orthogonal set from the 20 methods in the field guide; keep controls, one variable per causal comparison. Don't assume fusion, `f16`, workgroup size, offscreen or WebGPU always wins.
6. **Prove the value of the output.** For GPU rendering, capture *within* the timed pipeline when intermediate images matter; sample several locations / GPU hash or preserve full frames if required. Check actual foreground and changed content but do not equate sparse hash count with full unique frames. For simulation, read representative GPU state and compare a CPU/reference solver for equal steps, with error norms and conservation/boundary tests. For ML compare inference output, quantization error and pre/postprocessing. Report observation overhead separately.
7. **Report evidence with strict scope.** Label PHONE MEASURED / EXTERNAL DOCUMENTED / HYPOTHESIS. Give exact workload, pixels, steps, API, batch, warmup, duration, queue completion, observed output fraction, accuracy, uncertainty and sustained duration. Distinguish `GPU timestamp equivalent`, `queue-completed iterations/s`, `draw submissions/s`, and **externally verified** visible frames/s. Retain failures and rank only technical *strategies for a specified workload*, never invent unmeasured speedups.

## Quick routing rules

- **Physics/fluids that feed graphics:** keep solver fields in GPU storage buffers/textures; use ping-pong where read/write hazards demand it; run stages offscreen; choose independent solver/dye/visible resolutions by residual and quality; present/encode/sample only output the contract needs. Never copy solver state to Wasm every iteration without evidence.
- **Many independent particles:** WebGPU compute with state resident; test multi-step fusion (register pressure caveat); instanced/indirect render, cull and overdraw control; sweep N×steps separately from pixel count. SPH/PIC-FLIP need neighbor bins/scans and must not inherit independent-particle throughput claims.
- **Complex 3D:** profile CPU draw-call cost vs fragment load vs texture traffic; instantiate/batch, cull, cache probes/shadows if valid; use offscreen passes only when they save work or supply a required effect. Test Apple tile load/store choices portably; do not pretend WebGPU exposes native Metal memoryless allocations.
- **CPU irregular/small:** benchmark optimized JS vs Wasm SIMD and workers; thread support depends on *actual origin's* isolation. Transfer `ArrayBuffer` ownership where apt; SAB is not an aliased GPU buffer.
- **AI/images/maps:** retain GPU tensors/texture stages; fuse compatible operators, cache immutable assets, aggregate spatial data on GPU if enough volume; budget memory and compare end-to-end including conversions. GPU workload vs CPU transfer cost can change crossover point.
- **High-refresh observations:** worker rAF pacing is an *independently measured scheduler property*. Use main→worker relay to test 120 draw-submissions/s where appropriate, and **uncapped bounded GPU batches** to measure above-refresh completed throughput. These are different execution modes, neither inherently replaces the other.

## Known iPhone checkpoints (2026-09-21, specific exported configurations)

- Both WebGL2 and WebGPU lightweight main-thread and main→worker rendering probe: ~120 draw submissions/s; native worker rAF ~57–58/s. This does **not** measure scanout.
- Observed WebGPU fused 65,536×2 offscreen: 768×390, batch16 **1,199.36 queue-completed iterations/s**; 880×1738 batch16 **1,000.00/s**, batch64 **1,035.11/s**. Two 16×4 patches copied per frame; sparse samples change but full-frame uniqueness is unproven.
- Unobserved matching large scene (same suite, batch16): **994.42/s**; observation overhead not resolved by one short pair. Compute-only 262,144×8: **2,211.75 iterations/s**, not images. Benchmarks lasted ~2.5 s following ~1.6 s warmup, not sustained thermal tests.
- `GPUDevice.limits.maxBufferSize` **256 MiB** in observed export; do not conflate with earlier `GPUAdapter` limit or available RAM. Previous GitHub Pages report had `crossOriginIsolated=false` / SAB unavailable. These are origin/version observations, not universal hardware limitations.

## Stop conditions and next experiments

Stop an optimization claim when output changed, precision regressed, GPU device was lost, dimensions/quality differ without disclosure, the benchmark only times submission, or sample evidence is insufficient. Diagnose instead of guessing. First experiment for a new workload: an **output-contract ladder** at fixed resolution and data count—compute state only → state readback → offscreen render → sparse intermediate output observation → full intermediate output validation → visible canvas. Then sweep data size, solver steps, resolution, batch and API; run short peak and sustained tests separately. The field guide contains the concrete 20-method matrix and external references.

**Deliverable format:** one-paragraph findings with `what was measured / what was not`, concise per-case table, bottleneck hypothesis, exact code change and regression status (if code was changed), source/revision and raw JSON links, next most discriminating A/B test. Avoid a generic 'target 120 FPS' conclusion unless explicitly asked to optimize displayed animation.
