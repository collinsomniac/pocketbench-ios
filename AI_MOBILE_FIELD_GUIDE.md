# Mobile browser AI: throughput field guide and experiment ledger

**Research snapshot:** 2026-09-21. **Status:** research + a newly implemented, not-yet-iPhone-validated WebLLM benchmark. Companion: [AI benchmark](ai-bench.html), [global performance guide](PERFORMANCE_FIELD_GUIDE.md), [agent skill](skills/browser-throughput/SKILL.md). Never turn external/model-author numbers into this user's device measurements.

## 1. The performance objective is not display FPS

Maximize *correct, usable output per wall second* within the requested memory, quality, context and persistence requirements. A model can run entirely offscreen; the application may keep logits, KV cache, embeddings and intermediate activations GPU-resident, stream only generated token IDs/text to the UI, and perform unrelated rendering independently. An offscreen pipeline can do hundreds of operations per display refresh. It is not automatically faster *per operation*: it removes presentation coupling, allows batching/resolution changes and avoids unnecessary transfers. As PocketBench's particle experiments demonstrate, the useful unit and output-observation contract must be declared independently.

Separate: first-run **download bytes/time**, warm cached startup, engine compile/load, prefill prompt tokens/s, time-to-first-*visible text* (TTFT), decode generated tokens/s, full-request latency, outputs/s at batch/concurrent load, resident model+KV+scratch memory, correctness, and duration/thermal stability. Never equate streaming chunks or characters with tokens, or a catalog GPU-memory estimate with measured allocation. Token count is available only when the engine reports it or a matching tokenizer actually counts it. TTFT measured by JS includes browser and streaming overhead; it is not pure GPU prefill.

## 2. What is demonstrated, and on what device?

**PHONE MEASURED, user's iPhone, particle workload only:** [observed raw-summary ledger](benchmarks/2026-09-21-observed-summary.json) documents ~1,199 queue-completed offscreen-render iterations/s for 65,536 × 2 particles/steps at 768×390, and ~1,000/s at 880×1738 with sampled image changes. This is strong evidence of high throughput of that particular compute+render graph. It is **not a token/s estimate**, inference benchmark, full-frame-uniqueness proof, or NPU measurement. The mobile LLM column is currently **UNMEASURED on the user's device**.

**EXTERNAL AUTHOR-REPORTED browser data:** `svenflow/webgpu-gemma` reports iPhone 17 Pro Max / iOS 26 Safari (LambdaTest), Q8_0 Gemma 3 270M **101.1 generated tokens/s, TTFT 0.14 s**, and Gemma 3 1B **34.4 tokens/s, TTFT 0.45 s**. That is a promising speed/size point for one hand-built WGSL backend, not a cross-model quality comparison, not an independent replication, and not necessarily the user's iOS 27 Safari result. [Original project measurements](https://github.com/svenflow/webgpu-gemma/blob/main/README.md).

**EXTERNAL NATIVE APP, not browser:** an independently maintained Apple-silicon benchmark publishes substantially different token rates using MLX/Core ML/Core AI on iPhone 17 Pro. Those harnesses may use Metal/ANE and native memory APIs unavailable to ordinary webpages. Don't claim a browser can reach native speeds or Apple Neural Engine solely from a WebGPU adapter. [Native benchmark and methodology](https://github.com/john-rocky/apple-silicon-llm-bench).

**EXTERNAL caution:** WebLLM's own iOS 26 issue documents 135M successfully loading while a 3B model crashed the Safari tab after downloading; one device/report is not a universal limit. [WebLLM iOS report #753](https://github.com/mlc-ai/web-llm/issues/753). WebLLM also has a 2026 reported 0.2.83–0.2.84 shape-cache regression on an AMD iGPU; the report is not evidence of an iPhone regression. [Issue #844](https://github.com/mlc-ai/web-llm/issues/844).

## 3. Client-side execution routes (specific, not interchangeable)

| Route | What actually executes | When to try | Key constraints and experiments |
|---|---|---|---|
| [WebLLM 0.2.85](https://github.com/mlc-ai/web-llm) | MLC/TVM-compiled model library + WebGPU compute; tokenizer/runtime support in WASM; Cache API, IndexedDB and OPFS options | Full client LLM chat, quantized Qwen/Llama/other compatible catalogs; worker/main-thread A/B | Requires supported exact model **and** compiled model_lib, requested features, enough device resources; test q4f16 vs q4f32 and model/context sizes; download separately from inference. |
| [Transformers.js](https://huggingface.co/docs/transformers.js/) + [ONNX Runtime Web](https://onnxruntime.ai/docs/get-started/with-javascript/web.html) | ONNX operators assigned to WASM, WebGPU or other execution providers where supported | Embeddings, speech, vision, text generation and multi-task applications | Execution-provider support varies by OS/browser, operator and model; ORT's published support table currently marks Safari iOS WebGPU ❌ **for that library**, despite WebGPU itself working on this phone. Test real operator coverage, fallback copies and numerical parity. |
| [Custom WebGPU WGSL](https://github.com/svenflow/webgpu-gemma) | Hand-optimized kernels; GPU-resident weights/KV/cache, tailored format loaders | Fixed models/hot paths where generic operator overhead dominates | More engineering and maintenance; benchmark one model/quant equally on both backends before attributing a speedup; check attention/matmul kernel precision and cold load. |
| Wasm CPU / [wllama](https://github.com/ngxson/wllama) / llama.cpp ports | Wasm JIT on browser-accessible CPU; SIMD/threads when available | Fallback, small models, CPU-friendly ops, browsers without usable WebGPU | GitHub Pages often lacks cross-origin isolation for SharedArrayBuffer threads; **probe this origin** rather than assert all GitHub Pages are nonisolated. Worker scheduling and SIMD support vary. |
| WebNN | Browser-mediated ML API, potentially specialized hardware *if implementation and model runtime support it* | Experiment only after `navigator.ml` and ops support checks | Do not claim ANE access on iOS Safari; no portable JavaScript API exposes native Core ML/MLX or guarantees NPU routing. [WebNN compatibility](https://webnn.io/en/api-reference/browser-compatibility/api). |
| Native wrapper | Native Metal/Core ML/MLX APIs, optionally paired with web UI | When a real iOS app is in scope and native access is worth distribution costs | Fundamentally different security/memory and deployment boundary; do not label native iPhone tok/s as in-browser. |

WebLLM's source on 2026-09-21 reports package **0.2.85**. Its catalog is authoritative for exact IDs and estimated `vram_required_MB`; the PocketBench picker reads that catalog dynamically. ## 4. Candidate size/speed ladder: test, do not declare winners

Load **one model at a time**. The experiment offers only IDs present in WebLLM's actual catalog: SmolLM2 135M q0f16 if present; Qwen3 0.6B q4f16; Qwen3.5 0.8B q4f16; Llama 3.2 1B q4f16; Qwen3 1.7B q4f16; Qwen3.5 2B q4f16; Qwen2.5 3B q4f16. Start 0.6B to prove device/runtime success, try 0.8B and 1.7B next, and move to 2–3B only after recording memory/failures. The 270M/1B Gemma author-reported points above motivate a **separate model-and-backend experiment**, not an apples-to-apples speedup claim against Qwen.

Theoretical weight-only *lower bounds* (before quantization metadata, fp16 scales/embeddings, activations, KV cache, shader scratch, browser allocations): 0.6B at 4 bits ≈ **300 MB**; 0.8B ≈ **400 MB**; 1.7B ≈ **850 MB**; 3B ≈ **1.5 GB**. Actual compressed transfer size and peak memory may be substantially different. Use the catalog estimate as a planning hint, and browser `storage.estimate()` only as *origin-storage quota/usage*, not RAM/VRAM. A reported `GPUDevice.limits.maxBufferSize=256 MiB` is a *per-buffer limit*, not total GPU memory; model weights may occupy many buffers.

**Quality/size speed Pareto:** Do not choose only tok/s. Record instruction completion, structured-output validity, prompt/context length, language/tool-use performance and correctness on a fixed task set. Small models may deliver much higher generation rates yet fail a task that a 1–3B model completes. Distinguish text generation, embedding vectors/s, image or audio frames/s, and perception latency; they aren't interchangeable.

## 5. High-value optimization mechanisms, by measured bottleneck

1. **Download/cold-start-bound:** choose model architecture/format and quantization with fewer transferable bytes; test Cache API versus OPFS where implemented; stream/range-fetch shards where engine supports it; track downloaded *real* bytes separately from estimated memory; avoid auto-downloading multi-GB models. Revisit cache eviction and resume behavior.
2. **Weights/memory-bandwidth decode-bound:** compare lower-bit weights with the same model and task, group-wise quantization, operator fusion, packing and per-layer residency; measure dequantization overhead and quality. Native Metal and browser WGSL kernels can make the same nominal 4-bit weights perform differently.
3. **Prefill compute-bound:** efficient GEMM tiling/attention, chunking, fused normalization/activation, parallel prompt processing. Changing prefill chunks trades scratch memory against repeated overhead and may prevent OOM.
4. **Long-context KV-bound:** grouped/multi-query attention, compact KV cache, window/sliding attention when the model supports it, prefix reuse across actual matching prompts. Approximate KV footprint: `2 × layers × KV_heads × head_dim × cached_tokens × bytes_per_element × batches`; include implementation overhead and model details. Never truncate context while comparing equal-quality long-prompt capability without disclosure.
5. **Host↔device-bound:** retain weights, activations, logits and KV GPU-resident; avoid a CPU readback between operators or token steps; transfer only sampled token/needed data. [WebLLM discussion of GPU-resident sampling](https://github.com/mlc-ai/web-llm/pull/779) is ongoing work, not guaranteed current production capability.
6. **Small-kernel dispatch/JS-bound:** fuse adjacent operators if live values fit registers/workgroup memory; preallocate tensor buffers and reuse prepared graphs; compare main vs worker only on equivalent model/workload. Run compute without `requestAnimationFrame`; let the output consumer decide when to render. This is the same architecture lesson as PocketBench's uncapped particle pipeline.
7. **Parallelism/concurrency-bound:** sweep single stream vs concurrent inference with completed aggregate tokens/s, per-request TTFT, peak memory and quality; batches may raise aggregate throughput while reducing per-user latency. Browser GPU command queues and model instances can contend.
8. **Algorithm-bound:** speculative decoding, early exit, MoE expert routing, hybrid SSM/attention or model distillation are *model/runtime-specific features*, not switches. WebLLM speculative decoding is an [open feature request](https://github.com/mlc-ai/web-llm/issues/840); do not claim current support. Test draft-model accuracy, acceptance, extra memory and true end-to-end speed.
9. **Sustained/energy-bound:** run cold, warm and 60–180 s sustained separately; note device temperature externally if instrumented, low-power/charging conditions and tab reloads. Browser JS has no reliable general-purpose iPhone GPU temperature, VRAM, or Neural Engine telemetry.

## 6. PocketBench AI experiment v0.1: exact procedure

Open [ai-bench.html](ai-bench.html) in Safari. The page probes WebGPU and imports **pinned** WebLLM 0.2.85, but **does not download weights without an explicit Load model tap**. Select a model and main-thread or dedicated-worker engine, tap Load, then Run. Default two passes each of short and medium synthetic prompts, deterministic temperature=0/seed=42, output cap 96 model tokens, plus a warmup request. Optionally add a longer prompt or increase repeats. Only one model is loaded at a time. Stop requests take effect after the current inference; a fatal browser tab kill cannot be caught, so every finished case is locally persisted when possible.

Capture: exact catalog model ID, quantization suffix, catalog-estimated GPU memory and required features; runtime version; UA and viewport; GPU adapter features/limits; origin isolation, WebNN exposure, storage-quota estimate; selected worker/main execution path; load wall time (cold-vs-cached **not automatically inferred**); warmup; per-case input length, model-reported prompt/completion token counts when available, first-visible-text latency, model-reported prefill/decode rates when available, cautiously derived decode rate, end-to-end tokens/s, error and truncated output preview. Save full JSON via native Share or download. The original prompt is fixed in source and the output preview is limited to 240 characters; review report content before sharing.

**Known limitations:** The current experiment only benchmarks WebLLM WebGPU, not WebGL or WebAssembly inference; worker import/CDN and model compatibility require iPhone execution; `navigator.gpu` is not proof a model will load; JS first-visible-text timing differs from engine TTFT; prompt profiles are synthetic; cached load, peak RSS, energy, numeric accuracy and physical display FPS are not measured; external benchmarks are not equivalent tests. It records real failures rather than silently changing backend. Main-vs-worker model tests can be run sequentially, not concurrently, to avoid memory contention. Exact WebLLM package and model-lib versions need re-verification when pinning future runs.

## 7. Next experiment matrix / revision rules

A. Run 0.6B short+medium worker, then main path, alternating ABBA with a warm cached model; repeat 0.8B/1.7B only after the small model succeeds. A failure is a result, not permission to assume iOS can't run that size.

B. Hold model/quant/weights fixed and sweep prompt tokens ≈32/256/1024/2048 and generated tokens 32/128, preserving same task. Derive actual input/output token counts from usage. Inspect prefill vs decode; distinguish first-load from warm-cache times.

C. Compare WebLLM and custom GGUF WGSL/Transformers.js only where matching model, weights, quant, context and output requirements can be established. Otherwise report a **cross-product performance frontier**, not a backend speedup ratio.

D. Add a browser-local **embedding** case (small ONNX, WASM vs WebGPU with same weights), with vectors/s, dimension, cosine/element error and model load. Probe WebNN separately only if navigator.ml and provider can actually run it.

E. Sweep cache backend, context window, quantization, prefill chunk, batch/concurrency, worker/main, and long-duration stability **one factor at a time**. Check model output parity and record negative results; update this guide and the agent skill with source, revision, device, test case, failure or speedup and limits.
