# Maximum useful browser throughput

Read [`../../AGENT_PERFORMANCE_SKILL.md`](../../AGENT_PERFORMANCE_SKILL.md) as the operating procedure and [`../../PERFORMANCE_FIELD_GUIDE.md`](../../PERFORMANCE_FIELD_GUIDE.md) for the full evidence ledger, 20 optimization techniques, architecture decision table, fluid walkthrough, caveats, and research links. **For client-side model inference, also read [`../../AI_MOBILE_FIELD_GUIDE.md`](../../AI_MOBILE_FIELD_GUIDE.md) and use the real [`../../ai-bench.html`](../../ai-bench.html) experiment.** If those files are unavailable, apply the core steps below. Do not invent an unmeasured speedup.

**Goal:** maximize correctly completed computational units per elapsed wall second for the requested output contract. Never silently impose 60/120 FPS caps or reframe an uncapped compute task as display smoothness. Separate physics/solver rate, GPU-queue-completed iteration rate, sampled output change, draw-submission rate, and independently measured physical display refresh. **Offscreen and GPU-resident computation are valuable first-class architectures: measure avoided transfers/presentation coupling and actual extra passes instead of treating them as suspect.**

**Process:** (1) Define completed unit, correctness tolerance and required consumer: latest GPU field, every intermediate texture, only sparse features, CPU-readable pixels, or visible presentation. (2) Probe the actual deployment: API/feature availability, adapter *and device* limits, dimensions/DPR, extensions, worker scheduler, origin isolation and lost-device events. (3) Establish equivalent JS/Wasm/WebGL/WebGPU controls where expressible, including transfers, uploads, render and output requirements. (4) Collect raw timings with warmed paired repeats, bounded GPU-queue-completion batches for uncapped throughput, asynchronously sampled pass timestamps, observations and reference-state checks. (5) Locate the dominant cost: algorithmic complexity, transfer, memory traffic/locality, overdraw, CPU encoding, synchronization, allocation, rasterization or browser presentation. (6) A/B one targeted technique, verify numerical/visual equivalence and end-to-end unit throughput, document losses. (7) Report exact workload, measured scope, confidence, next discriminating test.

**Architecture pointers:** fluid solvers usually advance ping-pong GPU textures offscreen and render the resulting dye/mesh separately; particle integration uses resident GPU state, with neighbor search/sorting required for SPH/PIC-FLIP; browser games use offscreen passes for shadow/reflection/postprocessing/reuse, not inherently faster shaders; Wasm runs on CPU, with SIMD and threads only if the deployed origin permits them; WebGPU offers compute/storage, WebGL2 offers shader/FBO techniques and may outperform WebGPU on a given driver. On Apple tile GPUs optimize load/store and transient pass lifetimes portably but do not claim direct native Metal memoryless access from WebGPU. Prefer GPU-resident intermediates to repeated CPU round trips.

**Mobile AI / LLM route:** distinguish external author-reported results, this device's actual LLM results (currently none), and native iOS app results. A separate WebGPU Gemma author reports 101.1 tok/s for Gemma 3 270M and 34.4 tok/s for 1B on an iPhone 17 Pro Max; these are *not* PocketBench measurements or equal-workload WebLLM comparisons. Load model weights only after explicit user action. Test exact runtime+model+quantization+context; first load vs cached load; worker vs main; model-reported prompt/completion tokens; first-visible-text time vs model-provided prefill/decode speeds; model quality and failures; longer prompt and sustained runs. Never count stream chunks as tokens, treat catalog VRAM as actual RAM, assume WebGPU implies usable WebNN/Neural Engine, or import native Core ML tok/s as browser results. Prefer GPU-resident KV/activations/weights and minimal CPU readback when measurements support the pipeline. See the mobile AI guide for candidate model IDs, memory/quantization caveats, runtime compatibility and experiment design.

**New: mobile inference crash triage (2026-09-21):** The actual user recording shows Qwen3 0.6B q4f16 in the worker *loading successfully* then the page resetting at first 16-token warmup with no caught error visible. That does not prove memory exhaustion or a WebGPU-wide limit. Before retrying, use [`../../ai-diagnose.html`](../../ai-diagnose.html) and [`../../AI_CRASH_DIAGNOSIS.md`](../../AI_CRASH_DIAGNOSIS.md). Persist phase/model/path/token-count/stream mode to localStorage **before** every awaited GPU request; on an unclean reset preserve and export the checkpoint before a new test overwrites it. Test 135M control → identical one-token request on failing Qwen → four tokens → 16 streamed → same model on main thread; change only one variable. Record first visible output and caught worker/window errors; a silent reload is not an exception stack trace. A model-ready result is not inference-success evidence. Avoid automatic crash loops, giant default prompts, speculative device-compatibility claims, and clearing model cache without a reason. Record regression only after running the same compatible model and output on both runtimes.

**Known device evidence, NOT universal:** 2026-09-21 user iPhone, WebGPU fused 65,536 particles × 2 steps, observed small 768×390 offscreen target: ~1,199 queue-completed iterations/s; observed large 880×1738: ~1,000/s batch16 and ~1,035/s batch64; heavy compute-only 262,144 × 8: ~2,212 iterations/s without images. These are short runs with 1.6 s warmup and sparse two-patch observation, not full-image uniqueness or display FPS. Main-thread and relayed-worker lightweight graphics reached ~120 draw submissions/s while native-worker rAF was ~58/s. Current origin previously lacked cross-origin isolation and SAB; re-probe. Full provenance and limitations are in the field guide.

**Output:** concise evidence-backed decision and a falsifiable experiment, not a generic checklist or 'optimize for 120 Hz' conclusion. Update the evidence ledger only from verified reports; keep hypotheses separate. Respect device resource limits, memory budgets, foreground/thermal behavior and actual user output semantics.
