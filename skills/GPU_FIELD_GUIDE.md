# Browser Compute & Graphics: Throughput Field Guide

**Version:** 2026-09-21 research snapshot · **Purpose:** choose the fastest *correct* execution architecture for a workload, not merely fit a display refresh budget. This is a working performance handbook, **not** a claim that every suggested optimization was benchmarked on this iPhone. Companion: [AGENT_PERFORMANCE_SKILL.md](AGENT_PERFORMANCE_SKILL.md).

## 0. Vocabulary and evidence contract

**Different units are not interchangeable.** Report (a) CPU work/s and units/s, (b) GPU-queue-completed simulation/render iterations/s, (c) per-pass GPU timestamp durations, (d) changing/observable intermediate output rate and correctness, (e) browser canvas draw submissions/s, (f) externally measured actual displayed unique frames/s and input-to-photon latency if instrumentation exists. A 120 Hz screen is not a 120-iteration/s GPU limit. Conversely, `queue.onSubmittedWorkDone()` confirms all work submitted before the call has been processed; it does not establish physical display presentation, unique full images, or unbounded peak speed. Benchmark batch size, warmup, framebuffer dimensions, and observation overhead are part of the workload. Avoid calling offscreen iterations 'screen FPS'. [GPUQueue completion](https://developer.mozilla.org/en-US/docs/Web/API/GPUQueue/onSubmittedWorkDone).

Evidence labels: **PHONE MEASURED** = actual export from this device and exact configuration; **EXTERNAL DOCUMENTED** = referenced API or real system; **ENGINEERING HYPOTHESIS** = candidate requiring direct A/B and correctness checks. Preserve negative findings and measurement provenance.

## 2. Choose the output contract *before* choosing an API

| Contract / workload | Candidate architecture | What offscreen means | Critical test |
|---|---|---|---|
| Independent particle trajectories / N-body approximation | WebGPU storage-buffer compute + GPU billboard rendering; CPU/Wasm baseline at small N | Particle state always GPU-resident; render only when needed, possibly lower-res and composited | Updates/s at N×S; position/velocity error after equal simulated time; render resolution and overdraw sweep. |
| Eulerian 2D fluid / dye | GPU velocity, pressure, divergence, and dye textures; WebGPU compute or WebGL2 fragment passes | The simulation **is a chain of offscreen textures**, not a picture secretly shown elsewhere | Cell-updates/s at grid size × solver iterations, divergence residual, stability, dye quality; final compose only if needed. |
| SPH / PIC / FLIP particles | WebGPU spatial binning/prefix sums + particle/grid stages; CPU/Wasm for small N/control | GPU particle/grid fields; render surface, splats or mesh as separate consumer | Correct neighbors, density/energy error, sorting cost, memory footprint, render cost. |
| 3D scene / game | Raster geometry to visible canvas; offscreen shadows, depth, reflections, bloom, temporal cache as needed | Shadow/reflection/prepass targets used later, often **additional** work | Pass-by-pass GPU time, resolution/overdraw, draw-call CPU, final presentation separately. |
| Maps / huge point clouds | GPU aggregation/culling/instancing, cache tile textures/geometry; draw visible subset | Aggregate/bin/pick resources stay on GPU until requested | Points aggregated/s, memory, panning latency, query cost. |
| Images/video / camera effects | WebGPU texture compute/fragment chain, WebGL2 FBO, or CPU/Wasm SIMD depending on size and formats | Filter stages and temporary images; avoid full CPU readback between stages | Pixels/s, upload/convert/download time, end-to-end quality; codec paths may be separate browser APIs. |
| In-browser AI inference | WebGPU tensor operators and retained GPU tensors; Wasm SIMD for CPU-friendly models and preprocessing | Intermediate activations and KV caches remain on device; output only needed tokens/results | Tokens/s or inferences/s, first-token latency, max resident model/activation memory, model accuracy. |
| CPU-heavy irregular algorithms | Wasm SIMD + workers, JS optimized typed arrays; GPU only for suitably parallel kernels | No graphics target necessary | End-to-end input→output including JS↔Wasm and GPU transfer. |

**No unconditional winner.** WebGPU adds native-feeling compute/storage interfaces and is a strong candidate for large parallel jobs; WebGL2 still supplies widely used fragment/FBO and transform-feedback techniques and can outperform a particular WebGPU implementation; Wasm is CPU code, not a GPU API; JavaScript can win on tiny work by avoiding setup. The right comparison uses *same semantics, same output requirements and quality, same dimensions, complete elapsed time*. Document API/feature fallbacks, not a universal speed ordering.

## 3. Onscreen, offscreen, hybrid: the actual mechanism

- **Visible GPU canvas:** `GPUCanvasContext.getCurrentTexture()` provides a texture intended for later compositing; a WebGL canvas similarly participates in browser composition. Browser rendering-update policy, canvas scale, color format, compositing, and buffering may limit **submissions or presentation**, independent of offscreen shader throughput. [Canvas context](https://developer.mozilla.org/en-US/docs/Web/API/GPUCanvasContext/getCurrentTexture).
- **Offscreen GPU texture:** render/compute into a texture not automatically composited. It can be updated thousands of times per second and later sampled by shaders, copied into a history pool, reduced to features, or read to CPU. **The same shaders are not intrinsically faster merely because the destination is offscreen**: eliminating compositor interaction, reducing resolution, transient storage, avoiding presentation dependencies, or reusing results can make the *system* faster; extra render passes or full-frame texture copies can make it slower.
- **Worker `OffscreenCanvas`:** changes JavaScript ownership/thread, **not** by itself an offscreen-only GPU target. Its canvas can be displayed when transferred from a DOM canvas. Our iPhone's native worker rAF was ~58 Hz, while main-thread-paced worker delivery reached ~120/s; this is a **measured browser/path quirk**, not a rule for every iOS version or workload.
- **Hybrid:** run expensive solver stages uncapped into GPU-resident state/texture(s), have another consumer use selected snapshots or reduced summaries; decouple **compute cadence** from canvas draw cadence. Do not assume concurrent compute+render overlap on one GPU: dependencies, queue ownership and driver scheduling may serialize. Decide whether latest-only state, ring-buffer history, temporal accumulation, or *every intermediate image* is required. A full-screen copy at every solver iteration may erase the benefit.
- **Why games render offscreen:** shadow maps, water/reflections, depth prepasses, deferred lighting G-buffers, SSAO/bloom, dynamic resolution, temporal effects, occlusion and cached probes all need intermediate buffers. They are a means of reuse, quality, culling or memory locality; not a way to display more distinct frames than physical refresh. If the product is video encoding, offline rendering, ML input or scientific analysis, those offscreen outputs can be the **actual deliverable**, not throwaway work.

Apple documents tile-based deferred rendering and reducing off-chip traffic with judicious load/store actions and transient tile resources. **Do not claim WebGPU gives direct access to Metal's `storageModeMemoryless` or imageblocks.** WebGPU `loadOp`, `storeOp: 'discard'`, texture usage, and pass grouping are the *portable levers*; driver mapping is implementation-specific. If a texture is consumed by a later pass, its data must survive appropriately. [Apple tile-renderer discussion](https://developer.apple.com/documentation/Metal/rendering-a-scene-with-deferred-lighting-in-swift), [Metal load/store](https://developer.apple.com/documentation/Metal/setting-load-and-store-actions), [WebGL invalidateFramebuffer](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

## 4. Fluid simulation: yes, run most of it offscreen

**Grid-based 2D incompressible fluid (Stable Fluids family):** maintain ping-pong velocity textures `V0/V1`, dye `D0/D1`, pressure `P0/P1`; divergence field `div`; optional vorticity and obstacle fields. Encode passes roughly `splat → advect velocity → diffusion/vorticity (optional) → divergence → repeated Jacobi pressure iterations → subtract gradient → advect dye → [optional bloom/lighting] → sample dye in final canvas pass`. Many reads/writes are **GPU texture↔GPU texture**. Avoid round-tripping every step through JS/Wasm. Ping-pong is mandatory when a pass cannot safely read and write the same resource; synchronize cross-pass dependencies by ordered commands. A solver might use, *for example*, a 128² or 256² velocity/pressure grid and a separate higher-resolution dye/display texture—different numerical and visual resolution are deliberate, testable choices, not one universal configuration. Measure pressure residual and boundary correctness when reducing iteration count or precision. [GPU Gems: Fast Fluid Dynamics](https://developer.nvidia.com/gpugems/gpugems/part-vi-beyond-triangles/chapter-38-fast-fluid-dynamics-simulation-gpu); [WebGL fluid reference](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation); [WebGPU fluid ping-pong implementation](https://github.com/mikerkoval/FluidSimulation).

**Particles and neighbors:** independent particles (our benchmark) do **not** prove SPH performance: SPH introduces spatial bins, neighbor lookup, atomics/sorting/prefix scans, and irregular memory access. PIC/FLIP adds particle↔grid transfers. Benchmark binning, solve, and surface draw separately, and check conservation/density. [WebGPU SPH/PIC-FLIP example](https://github.com/jeantimex/fluid).

**Hybrid examples:** compute velocity/pressure at low solver resolution offscreen, retain state, render smooth dye at higher resolution; simulation emits sparse particles/foam or field texture consumed by a separate 3D surface renderer; compute a low-resolution shadow/reflection map and reuse it across several visible frames; perform one visible composition from the newest acceptable finished field. None of this requires capping solver throughput at 120 updates/s. Distinguish simulation **physical time** from how fast a benchmark deliberately advances it.

## 5. WebGPU / WebGL / Wasm / browser-hardware boundary

**WebGPU**: Web-exposed, validated GPU command and resource API. WGSL compute shaders, storage buffers/textures, render/compute pipelines and bind groups; `GPUQueue` for ordered submission. You cannot issue arbitrary Metal commands, request guaranteed hardware clocks/cache size, choose native Metal memoryless allocation, get privileged GPU counters, or assume all optional features. Check `adapter.features`, `adapter.limits`, `device.features`, `device.limits`, `device.lost`, format support and real pipeline compilation. Timestamp queries, shader-f16, ASTC and float formats must be probed and requested when optional. Request only needed limits to preserve portability. Render-target format must support intended blend/write/read use. Avoid `mapAsync`/queue drain inside every production iteration: use asynchronous GPU-to-GPU pipelines and bounded in-flight buffers; draining per **benchmark batch** is useful for throughput accounting. [WebGPU optimization examples](https://webgpufundamentals.org/webgpu/lessons/webgpu-optimization.html), [device requests](https://developer.mozilla.org/en-US/docs/Web/API/GPUAdapter/requestDevice), [queue semantics](https://developer.mozilla.org/en-US/docs/Web/API/GPUQueue/onSubmittedWorkDone).

**WebGL2**: GPU raster/fragment shaders, framebuffer objects, texture ping-pong, transform feedback (where suitable), instancing, timer-query extension when present. No portable general compute-shader API. Check float-render/blend and compressed texture extensions independently. Batch draws, freeze FBO/VAO state, use immutable `texStorage`, use `invalidateFramebuffer` for throwaway attachments, avoid synchronous `readPixels`, `finish`, hot-loop getters and surprise texture uploads; use pixel-pack buffers/fences for async readback where supported. `flush()` can encourage submission outside rAF, but does not certify GPU completion. [MDN WebGL performance guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

**WebAssembly/JS**: runs on CPU, can use Wasm SIMD (`-msimd128`) and worker parallelism. Wasm threads require SharedArrayBuffer / cross-origin isolation on the deployed origin, commonly COOP+COEP; our GitHub Pages test reported them unavailable, so never silently select pthreads. Large transferred `ArrayBuffer`s can move ownership without cloning; SAB is shared memory, **not** a WebGPU buffer alias. A CPU→GPU transfer is still an explicit API operation on unified-memory hardware, and avoiding unnecessary transfers still matters. Compilation, memory growth, JS↔Wasm crossings, copies and thread coordination can dominate a small job; compare against optimized JS typed arrays. [Emscripten SIMD](https://emscripten.org/docs/porting/simd), [pthreads](https://emscripten.org/docs/porting/pthreads), [MDN SAB](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer), [transferables](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers).

**iOS/browser boundary:** WebKit introduced WebGPU in Safari 26.0; actual browser/embedded view/version, GPU adapter selection, power mode, canvas dimensions, feature flags and worker scheduler can alter results. Our observed Safari report's UA contains inconsistent OS/version fragments; never derive exact chip/OS build from UA alone. Browser APIs do **not** expose a reliable GPU VRAM amount, GPU cache occupancy, sustained clock or device temperature. Apple GPUs have shared system memory and tile-rendering characteristics, but JS does not acquire direct control of physical cache allocation or guaranteed zero-copy GPU↔Wasm shared memory. [WebKit Safari WebGPU announcement](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [WebKit animation-frame explainer](https://webkit.github.io/explainers/animation-frame-rate/).

## 6. The 20 high-leverage optimization methods (ordered by *diagnostic fit*, not guaranteed speed)

| # | Technique / best-fit bottleneck | Implementation experiment | Evidence/check and failure mode |
|---:|---|---|---|
| 1 | **Keep intermediates GPU-resident**; upload/download cost | Chain compute/render passes over GPU buffers/textures; read only final sparse output | Compare end-to-end including transfer; GPU memory growth/context loss. [ONNX IO binding](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html). |
| 2 | **Fuse dependent passes**; repeated memory traffic | Integrate S independent-particle steps in registers, one load+store; fuse compatible image operators | Our 262k×8 compute-only baseline ~2.106 ms vs fused ~0.390 ms GPU pass in prior relay run. Verify numeric equivalence; register pressure/spills can reverse gains. |
| 3 | **Separate compute, output and presentation**; scheduler ceiling | Uncapped solver→offscreen state; rendered consumer with explicit history/latest-policy | Our observed small/large offscreen ~1,199/~1,000 iterations/s vs 120 Hz display. Do not label these visible FPS. |
| 4 | **Batch submissions/draws**; CPU/API overhead | Multi-dispatch command buffer, instancing, atlas, draw-indirect where supported; sweep batch 1/4/16/64 | Count GPU-completed work; large batches increase latency, memory and watchdog risk. |
| 5 | **Exploit data locality / workgroup staging**; redundant neighbor reads | Tile grid neighborhoods into `var<workgroup>` for stencil, spatial binning; benchmark 64/128/256 threads | Check occupancy, barriers, halos, workgroup storage and divergence; no universal ideal size. |
| 6 | **Avoid overdraw / prune before raster**; fragment load | Frustum/occlusion/cluster culling, cap billboard size, compact visible particle list | Measure covered pixels, fragments, compute+cull cost, particle fidelity. |
| 7 | **Lower independent resolutions**; pixel pressure | Velocity grid vs dye grid vs screen output vs shadow/bloom targets | Compare quality residual and cost by grid and framebuffer dimensions; 0.5 scale means 1/4 pixels, not half. |
| 8 | **Use narrow formats / quantified precision**; bandwidth and memory | Test `f16`, RG16F/RGBA16F, packed state where supported | Feature-check, quantization error, accumulation and precision stability; 16-bit is not always faster. |
| 9 | **Choose buffer layout for access**; cache/coalescing | AoS 32B particle vs split SoA position/velocity; alignment-aware packing | Sweep N, S; include conversion and draw stage; SoA not automatic winner. |
| 10 | **Ping-pong/reuse preallocated resources**; allocations and hazards | Fixed pools for textures/buffers, alternate read/write, stable bind groups | Memory telemetry/creation counts, dependency validation; avoid disposing in-use GPU objects. |
| 11 | **Reduce render-target load/store**; tile-memory traffic | `loadOp:'clear'` vs load; `storeOp:'discard'` only if unneeded, merge passes when legal | Pixel correctness for consumers; native Metal memoryless is not a direct WebGPU API. |
| 12 | **Avoid synchronous CPU↔GPU stalls**; queue idle | Defer map/readback; ring readback buffers; async fences; sparse sampling | Compare queue throughput plus age of results; benchmark drains intentionally only per batch. |
| 13 | **Minimize pipeline/bind changes**; CPU driver overhead | Cache shader modules, pipelines, bind groups; sorted draw order, render bundles when appropriate | Cold vs warm pipeline cost, many-object scenes; excessive cache can exhaust memory. |
| 14 | **Cache and reuse valid work**; repeated inputs | Static shadow maps, temporal history, spatial tiles, ML KV cache, cached geometries | Invalidate on actual dependency change, bound memory and stale-output error. |
| 15 | **Use GPU aggregation / indirect compaction**; CPU O(N) preprocessing | Grid bin/reduce; prefix scan; indirect draw counts | Compare upload+compute+readback with CPU, handle device differences. [deck.gl](https://deck.gl/docs/api-reference/aggregation-layers/overview). |
| 16 | **Select SIMD/threads for CPU-shaped problems** | Wasm `-msimd128` and cross-origin-isolated worker pool versus optimized JS | Test deployed headers, thread count, oversubscription and data ownership. |
| 17 | **Reduce unnecessary shader arithmetic** | Move shared math from fragment to vertex, precompute invariants, favor built-ins | Visual/numeric check, GPU timestamps under actual coverage, compiler may already optimize. |
| 18 | **Compress assets/textures on GPU**; texture bandwidth and download | ASTC/ETC2/BC capability-specific path, transcode Basis/KTX2 once | Measure load time, GPU size, texture sample time, quality; compression not suitable for all simulation fields. |
| 19 | **Separate cold-start and hot-loop costs** | Precompile pipelines, reuse buffers, warmup, record first-run and warmed steady-state | Our earlier 54-ms 16-frame batches dropped near 13 ms; reason unknown; never infer a GPU clock from this alone. |
| 20 | **Profile end-to-end and seek bottleneck shifts** | Orthogonal sweeps: N, steps, pixel scale, batch, shader complexity, API, transfer, capture | Record correctness + completed units/s + pass timestamps + wall latency; optimization of one stage can expose another. |

**Caching hierarchy in practice:** within one invocation use registers/private values; within workgroup use explicit workgroup memory only if reuse pays for barriers; on GPU across passes reuse storage buffers/textures and the hardware's opaque caches; on CPU reuse typed arrays/Wasm linear memory and preallocated arenas; persist immutable assets/models in Cache API/IndexedDB/OPFS if supported. JS cannot choose GPU L1/L2 addresses, pin GPU cache lines, or promise a buffer is 'in VRAM' on Apple unified memory. Use instrumented performance rather than cache folklore.

## 7. Real-world cross-discipline references and transfer lessons

1. **GPU fluids:** [GPU Gems Ch. 38](https://developer.nvidia.com/gpugems/gpugems/part-vi-beyond-triangles/chapter-38-fast-fluid-dynamics-simulation-gpu) and [Pavel Dobryakov's WebGL fluid](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation): feedback fields, many FBO passes, pressure/dye resolution, final display only. The lesson is GPU-resident *state* and selective final presentation.
2. **Modern WebGPU fluids:** [jeantimex/fluid](https://github.com/jeantimex/fluid) demonstrates SPH/PIC-FLIP, spatial sorting and distinct surface renderers: neighbor search, not mere particle integration, changes the algorithmic bottleneck.
3. **Mapping/analytics:** [deck.gl aggregation](https://deck.gl/docs/api-reference/aggregation-layers/overview) can group input on GPU and draw reduced geometry; their docs explicitly note fallback and differing CPU/GPU tradeoffs.
4. **ML inference:** [ONNX Runtime Web GPU execution provider](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html) supports GPU IO binding to retain tensors; graph capture for compatible static-shape GPU graphs; tests should measure full inference and transfers.
5. **Local LLMs:** [WebLLM](https://github.com/mlc-ai/web-llm) runs models in browser via WebGPU and caches downloaded weights in browser storage. Persistent **asset** caching is different from device-resident runtime KV/activation memory; cache growth and eviction are operational issues.
6. **Apple native rendering:** [Apple tile deferred sample](https://developer.apple.com/documentation/Metal/rendering-a-scene-with-deferred-lighting-in-swift) explains off-chip G-buffer traffic and tile residency, a useful architecture principle but **not** a promise the corresponding Metal feature is exposed in WebGPU.
7. **Scene batching:** [WebGPU Fundamentals optimization](https://webgpufundamentals.org/webgpu/lessons/webgpu-optimization.html) and [MDN WebGL practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) cover instancing, buffer/draw reuse, pixel budget, optional formats and avoiding stalls.
8. **Community warning, not measurement:** [September 2025 r/webgpu report](https://www.reddit.com/r/webgpu/comments/1nir8it) describes Safari/WebGPU regressions compared with WebGL in some animation scenarios; anecdotal device-specific experience motivates A/B rather than categorical claims. [August 2026 multi-device probe](https://www.reddit.com/r/webgpu/comments/1w1aavx/i_tried_to_prove_browsers_misreport_webgpu/) reported substantial cross-device differences in exposed limits and pipeline costs; independently remeasure because a forum post is not a specification.

## 8. Next benchmark matrix: advance knowledge rather than another benchmark-specific hack

All cases require correctness reference, shader/source revision hash, browser build, real canvas size, target format/usage, particle/grid count, solver steps, device and adapter features/limits, exact warmup, cooling/power/foreground notes, sample size, raw batch times, result bytes observed, and `device.lost`/error log. Randomize ABBA/repeated order where possible; do not treat sequential cases as independent replicates. Use bounded batches and explicit GPU-completion fences for *throughput mode*, never silently poll queue completion every production frame.

1. **Output contract sweep**: compute only → GPU state copy sampled → offscreen draw no observation → two-patch observation → full-image hash GPU compute → readback full image → actual canvas; hold N/S/dimensions constant. Tests what each requested observable costs.
2. **Resolution×overdraw**: 0.25/0.5/1.0 render scale, 8k/65k/262k particles and point size/coverage; distinguish full texture pixel writes from actual fragments. Measure separately raster, compute, compositor callback path.
3. **Kernel/layout**: original vs fused, AoS vs SoA, workgroup sizes 64/128/256, f32 vs supported f16; compare state error after **same number of steps**. Register spill risk at large S.
4. **Submission semantics**: batch 1/4/16/64/128; fixed target and same capture; report cold, warmed, median/P95 batch times, completed iterations/s and in-flight depth.
5. **Cross-API equal-workload**: WebGL2 FBO ping-pong (when expressible) vs WebGPU compute/render vs JS/Wasm SIMD, including upload, format conversion and readback. Don't compare different visual effects and call it an API win.
6. **Fluid-specific**: separate velocity grid/dye grid, Jacobi iteration count and residual, advection quality, curl/vorticity, SPH neighbor density and sort. Compare render-only consumers separately.
7. **Sustained behavior**: multiple 30–120 s sessions at varied workload/power with cooled control, completed-work sliding windows, memory growth, device loss and background behavior. Short peak and sustained rates are separate claims.
8. **Browser integration**: main thread vs native-worker rAF vs main→worker relay vs truly uncapped worker; Safari vs alternative available iOS browser/context; feature flags and page origin. Preserve independent physical display measurement as a separate project.

**Success criterion:** an agent can take a new workload, specify what constitutes a correct completed unit and required output, select a plausible engine without assuming API superiority, deploy paired experiments on the actual target, compute unit throughput, identify the changed bottleneck, and retain reproducible evidence. No explicit FPS cap is prescribed anywhere in this guide.
