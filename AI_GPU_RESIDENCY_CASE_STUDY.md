# Case study: GPU-resident LLM inference without a giant JavaScript weight copy

**2026-09-21 research note; external author evidence, not PocketBench iPhone measurement.** Source: [svenflow/webgpu-gemma](https://github.com/svenflow/webgpu-gemma), especially its [README and benchmark notes](https://github.com/svenflow/webgpu-gemma/blob/main/README.md). Also see [PocketBench's runtime bake-off](BROWSER_INFERENCE_STACK.md) and [independent GGUF experiment](ai-wllama.html).

The author reports these *specific* iPhone 17 Pro Max Safari/iOS 26 browser WebGPU results from LambdaTest: Gemma 3 270M Q8_0 **101.1 generated tokens/s**, first token **0.14 s**; Gemma 3 1B Q8_0 **34.4 generated tokens/s**, first token **0.45 s**. These numbers use different architectures/weights from PocketBench's WebLLM SmolLM2 135M Q0F16 runs (46.81–51.55 model-reported decode tokens/s), so **do not rank the models or runtimes as if the tests were equal**. The README says the 1B path needs about a 1 GB download and ~1.5 GB GPU memory, not browser-measured system memory.

**The architectural lesson is not just GPU arithmetic.** The project reports using HTTP Range requests to stream GGUF weights layer-by-layer in approximately 44 MB chunks; each chunk is uploaded to GPU, then the temporary JS bytes can be released. It claims peak JS-memory usage around 50 MB instead of keeping an entire 1 GB weight file in JS memory. It also describes 18 purpose-built WGSL kernels, GPU-resident weights and a reusable attention KV cache. Thus a model that fits in total device memory can still fail in a generic browser loader if it temporarily allocates a full model Blob, a separate ArrayBuffer, a Wasm copy and GPU buffers simultaneously. This is a **candidate mechanism**, not a proven cause of this user's WebLLM Qwen3 crash.

## Apply to PocketBench

1. Separate download bytes, peak JS staging, Wasm memory, GPU residency, KV cache and shader/scratch buffers in an accounting diagram; a browser's `maxBufferSize` is a per-resource limit, not a total VRAM figure. Where APIs do not expose actual usage, record **not observable** rather than inventing numbers.
2. For a model family with known architecture, build a specialized streamed range loader only after checking response `206 Partial Content`, valid `Content-Range`, CORS, total size, checksums, cache key/version and server behavior when Range is ignored. Never silently fetch the entire 1 GB artifact as a fallback on mobile.
3. Compare identical model+weights and prompt under full-file loader vs chunked upload if both work, measuring cold/cached load, crash point, JS staging high-water *when observable*, generated token rate, first token, output correctness and repeated context turns. `performance.memory` is not a portable iOS memory measurement.
4. Keep weights/activations/KV GPU-resident; benchmark per-layer dispatch overhead, matrix-vector decoding, fused operators and quantization/dequantization precision; avoid CPU round trips. Don't assume a smaller upload chunk is faster: too many range requests, decode stages or fragmentary GPU allocations can reverse the benefit.
5. A small fixed-model WGSL runtime may beat a general-purpose engine, but supports fewer architectures, formats and edge cases. Compare a generalized GGUF runtime and a specialized runtime under matching model configurations before investing in an in-house kernel stack.

**Runtime diversity:** The independent [wllama browser test](ai-wllama.html) isolates CPU-Wasm and optional GPU layer offload; a CPU success would show the model can execute through another browser code path. It does not validate efficient streamed GPU loading. The [LiteRT-LM Web API](https://developers.google.com/edge/litert-lm/js) is a separate early-preview WebGPU engine with explicitly web-compatible Gemma 4 assets; verify its package version and artifact support first. Magnitude's hardware profiling and dynamic-memory aspirations are useful software architecture inspiration but native-only; GitHub Pages cannot call its server, Metal, CUDA, or Apple's Neural Engine directly.

**Evidence gate:** Only promote claimed performance into the device ledger after an exported run on the user's exact browser/runtime/model and retained output. External numbers are examples of feasible architectures, not guaranteed speeds or crash fixes.
